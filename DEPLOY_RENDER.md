# MindGuard AI — Render deployment guide

This repository is prepared for Render, but it is **not deployed yet**. A public URL is created only after you connect a Git repository, provision MySQL, enter database credentials, and complete the first successful deploy.

## Important privacy warning

This is a college demonstration prototype. Do not enter real student mental-health information or invite real students until your institution has completed privacy, security, ethics, safeguarding, retention, backup, and incident-response reviews. Use synthetic demonstration accounts and data.

## Hosting architecture

- Flask web app: Render Web Service, served by Gunicorn over HTTPS.
- Database: MySQL 8 reachable by the web service. Render's own MySQL guide uses a private MySQL service with a persistent disk; alternatively use a trusted managed MySQL provider.
- Secrets: Render environment variables. Never commit `.env`, passwords, or database connection strings.

## A. Put the project in GitHub

1. Create a **private** GitHub repository named `mindguard-ai`.
2. Extract the release ZIP.
3. Upload the *contents* of `mindguard_fullstack/` to the repository root (so `app.py`, `render.yaml`, and `requirements.txt` are at the root).
4. Ensure `.env` is not uploaded. `.gitignore` is included.

## B. Provision MySQL 8

Create a MySQL 8 database on a managed provider or follow Render's current MySQL deployment guide:
https://render.com/docs/deploy-mysql

Use a private/network-restricted connection if available. Create a dedicated application DB user with only the privileges required by this app; do not use `root` for the web service. Note the host, port, database name, username, and password.

Import `schema.sql` into the empty `mindguard` database. For an existing database, apply any migrations that have not already been applied; do not blindly rerun migrations.

## C. Deploy the web service

1. Sign in to https://render.com/
2. Choose **New → Blueprint** and connect the private GitHub repository.
3. Render detects `render.yaml`. Review the service and choose a paid web-service plan suitable for your demo. The included blueprint uses `starter` to avoid a sleeping instance during a live presentation; change the plan in the Render dashboard if needed.
4. Before the first deploy, open the service's **Environment** page and set:
   - `MYSQL_HOST` = your MySQL hostname
   - `MYSQL_PORT` = database port (usually `3306`)
   - `MYSQL_USER` = dedicated app username
   - `MYSQL_PASSWORD` = dedicated app password
   - `MYSQL_DATABASE` = `mindguard`
   `SECRET_KEY` is generated by the blueprint. Keep it stable between deploys.
5. Deploy. The build command is `pip install -r requirements.txt`; the start command is Gunicorn.
6. Wait for the deploy to report **Live**. Test `https://YOUR-SERVICE.onrender.com/health` and then open the root URL.

Official docs:
- Flask deploy: https://render.com/docs/deploy-flask
- Environment variables: https://render.com/docs/configure-environment-variables
- Web services and HTTPS: https://render.com/docs/web-services

## D. Create a counsellor account

In the Render service dashboard, open **Shell** (if available on your plan) and run:

```bash
flask --app app create-counsellor
```

If Shell is unavailable, run the command in a secure one-off environment with the same environment variables and network access to the database. Do not create counsellors through public registration.

## E. Final smoke test

- `/health` returns `{"status":"ok", ...}`.
- Register a synthetic student, accept consent, and submit a synthetic check-in.
- Verify the student sees only their own records.
- Create a counsellor using the CLI; verify the counsellor sees appointment requests and thresholded aggregates, not individual check-ins.
- Test urgent support and privacy withdrawal/deletion with synthetic data.
- Confirm HTTPS and secure cookies. Never test account deletion on real users' data.

## Operational notes

- Render web services use an ephemeral filesystem by default; keep persistent data in MySQL, not local files.
- Back up MySQL using its supported backup procedure and define backup expiry/deletion before collecting any sensitive information.
- Keep database access private, rotate credentials if exposed, and monitor deployment logs without logging wellness values or passwords.
- The `/health` endpoint currently checks application process health, not MySQL readiness. Verify DB connectivity separately during the smoke test.
- This project has not been deployed or tested against a live hosted MySQL service. A successful public URL cannot be claimed until the steps above are completed.
